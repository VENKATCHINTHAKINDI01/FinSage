# Data-processing register — s.8(1)

Last reviewed 2026-08-16. Generated by reading the stores and routes that
exist today, not aspirationally — a register that lists a store nothing
writes to is as misleading as one that omits a store something does.

s.8(1) requires a Data Fiduciary to maintain a record of personal data
processing. This is that record: every store holding personal data, what it
holds, why, and how long, cross-referenced to `RETENTION_DAYS` in
`backend/compliance/dpdp/consent.py` and the purposes in `docs/dpdp_controls.md`.

## Stores

| Store | Table / location | Personal data held | Purpose | Retention |
|---|---|---|---|---|
| Postgres | `users` | Email, full name, password hash | Account / `TAX_COMPUTATION` (necessary) | Until account deletion; erasure via `erase()` on a confirmed request |
| Postgres | `financial_profiles` | Annual income, expenses, employment type, free-text financial goal | `TAX_COMPUTATION` (necessary) | 8 years from last activity (ITR-U window) — `RETENTION_DAYS[TAX_COMPUTATION]` |
| Postgres | `refresh_sessions` | User id, session family/state (no credentials) | Account security (PRD-002) | Row expires with the session; retained past expiry only as rotation-history evidence of a specific family until that family is superseded |
| Postgres | `consent_records` | Principal id, purpose, notice version, grant/withdraw dates | Compliance evidence — s.6 requires being able to show consent was held | Not itself subject to `RETENTION_DAYS`; append-only compliance evidence is the one category DPDP expects to outlive the data it authorised, so it is kept for as long as the account exists plus the underlying purpose's retention window |
| Postgres | `tax_calculations`, `itr_filings`, `compliance_reports`, `audit_history` | Computed tax figures, filing status, income sources referenced by the computation | `TAX_COMPUTATION`, `ITR_FILING` (necessary) | 8 years — `RETENTION_DAYS[ITR_FILING]` |
| Postgres | `red_flag_logs`, `financial_health_scores` | Derived risk/health indicators, not raw source documents | `TAX_COMPUTATION` (necessary) | 8 years, tied to the filing they were computed for |
| Postgres | `notifications`, `notification_preferences` | Delivery channel (email/telegram id), message content, send status | `MARKETING` for reminders the user can decline; `TAX_COMPUTATION`-adjacent for deadline alerts tied to a filing obligation | 400 days — `RETENTION_DAYS[MARKETING]` / `[PRODUCT_ANALYTICS]` |
| Object storage (S3/MinIO document vault, DOC-004) | Encrypted document blobs | Uploaded Form 16, AIS, broker statements — the source documents themselves, not just extracted figures | `DOCUMENT_STORAGE` (necessary) | 8 years — `RETENTION_DAYS[DOCUMENT_STORAGE]`; deletion requires vault-specific deleter/confirmer wiring into `erase()` (see the gap noted below) |
| Vector store (Qdrant) | RAG corpus embeddings | Product/knowledge-base content by design; **not** intended to hold user-specific personal data, but any document ingested through `/api/v1/knowledge/upload` without a scrub step lands here | `PRODUCT_ANALYTICS`-adjacent (retrieval quality) | Not currently covered by `RETENTION_DAYS` or `erase()` — see gap below |
| Application logs | `logs/finsage.log` | Request metadata; PAN, GSTIN, Aadhaar (Verhoeff-checked), email and phone are redacted by `RedactingFormatter` (PRD-004) before a line is written | Operational, not a purpose under s.6 | Governed by log rotation, not `RETENTION_DAYS` — no DPDP-specific retention policy exists for logs yet |

## Processors (third parties personal data is shared with)

| Processor | Data shared | Purpose |
|---|---|---|
| Groq (LLM inference) | The query text and whatever profile fields are included in the prompt context for a given request — no raw documents | Explaining a computed result (never computing it — `backend/core` never reaches an LLM) |
| Email/SMTP provider (`backend/services/notification.py`) | Recipient email, message content | `MARKETING` / deadline reminders, per `notification_preferences` |
| Telegram Bot API | Telegram chat id, message content | Same, for users who opted into that channel |

No sub-processor agreements or data-processing addenda are on file for any of
the above as of this writing — that is itself a gap, not an oversight being
hidden.

## Known gaps in this register

1. **Document vault and vector store are not wired into `erase()`.** The
   compliance module's `erase()` takes a per-store deleter/confirmer pair;
   Postgres tables have an obvious path (a `DELETE` plus a `SELECT` to
   confirm), but the vault and Qdrant do not yet have one implemented. A user
   whose consent is withdrawn today has their Postgres-resident data become
   due for erasure immediately (`due_for_erasure`), but the document PDF
   itself is not automatically part of that run yet.
2. **No retention policy for application logs.** They rotate on disk size/age,
   not on a DPDP-driven schedule.
3. **This register is maintained by hand.** A store added to `orm_models.py`
   without a corresponding row here is a real, quiet way for this document to
   go stale — the same failure mode `verify_freshness.py` exists to catch for
   tax rules, and this has no equivalent CI gate yet.
